## 2. 요청 1 — 손실률(`plr` 계열 · `_packetLossRate`)을 규격 단위(0.1 %)의 정수로 · **우선**

**현상.** AF `9_`(PERF_DATA) 통지의 `perfData` 에서 `plr` · `plrDl` · `maxPlrUl` · `maxPlrDl` 네 필드에 **소수**가 옵니다.
9월 30일 19:48 부터 10월 2일 19:33 까지 **119개 통지**에서 나왔고, 값은 `1.7` ~ `98.3` 입니다.
정수로 떨어지는 퍼센트(예: 9/30 19:47 `100`, 10/1 01:20 `15`, 10/2 07:53 `45`)는 형식 검증을 통과해 이 수에 들어가지 않았지만 같은 단위 문제입니다
(`45` 는 규격상 4.5 % 로 읽힙니다).

| 예 | 네 필드 값 |
|---|---|
| 가장 흔한 소수값(대부분 UE1 `192.168.101.10` — 평소 값은 `0`) | `1.7` |
| 9/30 19:55 · 19:57 | `18.3` · `76.7` |
| 10/2 19:05 ~ 19:33 (ACTIVE 이후 계속, §4) | `73.3` ~ `98.3` |

**규격.** 네 필드는 모두 `PacketLossRate` 로, **정수 0 ~ 1000, 단위 0.1 %**(tenth of percent)입니다
(TS 29.571, TS 23.501 5.7.2.8 — PoC 규격 `TS29571_CommonData_PoC_ETRI_DoDo1.yaml` 의 `PacketLossRate`).
보내 주시는 값은 **퍼센트를 소수 한 자리로 적은 것**으로 보입니다. 1.7 % 라면 규격 값은 `17` 입니다.

UPF `8_` 의 `_packetLossRate`(같은 `PacketLossRate` 타입)도 같은 원천이라, 형식은 통과하지만 **퍼센트를 올림한 정수**로 옵니다.

**원인 (9/28 소스 기준으로 추정).**
- 수집 서버가 손실률을 퍼센트 `%.1f` 로 DB 에 적재합니다(`nw_collect/collect_server/recv_server_db.c`).
- `Replace_Stamp_One()`(`src/ncof_flow_targeting.cpp:69`)이 그 문자열을 `@@UEn_LOSS@@` 자리에 그대로 넣습니다. 이 자리표시자는
  `9_`·`9p_`·`10_a`·`10p_a` 의 `plr` 네 필드와 `8_`·`8p_` 의 `_packetLossRate` 에 쓰입니다(예: `9_…tmpl:175-178`).
- 출력 정수화 목록 `Is_Ncof_Integer_Field_Local()`(`src/ncof_flow_common.cpp:816-848`)에는 `_packetLossRate` 만 있고
  `plr` 네 필드가 없어, `9_` 계열은 소수 그대로, `8_` 계열은 올림 정수로 나갑니다.

**요청.** DB 값은 그대로 두시고, **`Replace_Stamp_One()` 의 `@@…_LOSS@@` 치환에서 `round(값 × 10)` 한 0 ~ 1000 정수**를 넣어 주십시오
(1.7 % → `17`, 98.3 % → `983`, 100 % → `1000`). 그러면 위 여섯 템플릿이 한 번에 맞춰집니다.
- ⚠️ **정수화 목록에 `plr` 을 추가하는 것만으로는 부족합니다.** 그러면 올림 정수(1.7 → `2`)가 되어 형식 검증은 통과하지만
  값은 여전히 퍼센트라 규격상 0.2 % 로 읽힙니다(실제의 약 1/8). `_packetLossRate` 가 지금 이 상태입니다.
- 값이 없는 주기는 지금처럼 필드를 생략하시면 됩니다.

**여쭙는 것.** 관측값이 모두 n/60 을 퍼센트로 바꿔 소수 한 자리로 반올림한 값입니다(1/60 → 1.7, 44/60 → 73.3, 59/60 → 98.3).
손실률을 STAMP 프로브 60개(예: 60초 창) 기준으로 계산하시는지요?

저희는 지금 이 네 필드를 임시 보정 계층에서 반올림해 받고 있고, 이 때문에 보정 계층을 걷어 내지 못하고 있습니다.
보정을 끄면 이 통지들은 통째로 거절(422)되어 같은 통지에 실린 다른 UE 의 성능값까지 잃게 됩니다.

저희로서는 QoS 영향인지, 저장된 gNB2 상태에 따른 리포트 생성 방식인지 판단하기 어려워 여쭙니다.

1. 26321 을 받는 쪽이 **UPF 이고, 받은 값을 실제 세션 QoS 에 적용**하는지요? 적용되었다면 19:01:43 · 19:03:44 의 적용 로그를 부탁드립니다.
2. **RICF 성능 리포트(`10_a`)의 `192.168.1.122` · `192.168.1.123` 항목**이 무엇을 재는지요(gNB 단위 집계인지)? UE3 와 `.123` 이 `15f` 상태에 따라
   생략되는 것이 의도된 동작인지, `ACTIVE` 뒤 `.123` 의 77 Mbps 와 UE3 · UE4 손실률 73 ~ 98 % 가 실제 측정값인지 궁금합니다.
3. **IMSI 체계.** UPF `8_` 는 `192.168.104.10` 을 `imsi-001010000000004`(102.10 은 `…003`, 103.10 은 `…002`)로 보고하는데,
   QoS UDP 에는 `001010070000101` ~ `…104` 가 실립니다. UPF 는 어느 IMSI 로 세션을 찾는지요? 번호 순서도 달라서(예: 102.10 은 UPF `…003`,
   QoS UE3 `…102`), 슬롯과 UE 의 대응을 알려 주시면 감사하겠습니다.
4. **단위 · `0` 의 의미 · 유효기간.** 저희는 `"500.0 Mbps"` 처럼 보내는데 `std::stod` 에서 단위가 빠집니다. 평시 UE3 는 `0/0` 인데 UPF
   `filter-002-dl`(→ `192.168.102.10`)은 약 104 Mbps 라 `0` 이 차단이라면 맞지 않습니다. `0` 이 무엇을 뜻하는지(차단 / 무제한 / 미적용),
   적용 값이 언제까지 유지되고 어떻게 해제되는지 궁금합니다(저희 `14_e` 에는 유효기간 60초가 실립니다).

현재는 UDP 발사가 실패하거나 UE 4개가 다 차지 않아도 SBI 응답이 `200` 이라 저희 쪽에서는 적용 여부를 알 수 없습니다.
가능하시면 적용 결과를 로그로 남기시거나, 응답 본문에 발사 여부(예: `udp_sent`, `fill_count`)를 실어 주시면 좋겠습니다.

## 5. 참고 — 급하지 않은 항목

- **SBI 앱 자동 기동과 상향 구독 재시도.** 지금은 앱이 멈추거나 서버가 재부팅되면 저희가 NCOF 를 먼저 띄운 뒤 앱을 다시 올려야 합니다.
  자동 기동을 넣으실 경우 NCOF 보다 먼저 뜨면 상향 구독이 한 번만 나가고 끝나므로(`main.cpp:251-263`, 재시도 없음) 재시도와
  PCF · RICF 독립 송신도 함께 검토 부탁드립니다.
- **`13p_d` `_powerState`.** 물리 gNB 상태가 아니라 "마지막으로 받은 명령" 으로 이해하고 있습니다. 맞는지 확인 부탁드립니다.
- **`13p_d` `_duration` 리터럴.** `13p_d` 템플릿(53 · 114 · 173 · 219행)의 `_duration` 이 `60` 으로 고정되어 있습니다. 지금은 `repPeriod` 가
  60 이라 문제가 없지만, `repPeriod` 와 같은 값으로 치환해 주시면 좋겠습니다.
- **AF 성능값 생략.** 10/2 `ACTIVE` 뒤 UE4(`192.168.104.10`)가 한 주기 걸러(19:04 · 19:06 · 19:08 · 19:10) 통째로 생략되었습니다
  (UE3 와 `.123` 의 생략은 §4 질문 2).
- **`monDur` 고정값.** 12월 31일 12:00 에 같은 방식으로 만료됩니다. 1월 이후 시연을 위해 기동 시각 기준 상대값 방식을 검토해 주시면
  좋겠습니다.
