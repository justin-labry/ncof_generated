## 2. 요청 1 — 손실률(`plr` 계열 · `_packetLossRate`)을 규격 단위(0.1 %)의 정수로 · **우선**

**현상.** AF `9_`(PERF_DATA) 통지의 UE4 `perfData` 에서 `plr` · `plrDl` · `maxPlrUl` · `maxPlrDl` 네 필드에 **소수**가 옵니다

| 수신 시각 | 네 필드 값 |
|---|---|
| 19:48:34 · 19:50:34 · 19:59:39 · 20:07:43 | `1.7` |
| 20:03:42 | `3.3` |
| 19:55:35 | `18.3` |
| 19:57:37 | `76.7` |

**규격.** 네 필드는 모두 `PacketLossRate` 로, **정수 0 ~ 1000, 단위 0.1 %**(tenth of percent)입니다
(TS 29.571, TS 23.501 5.7.2.8 — PoC 규격 `TS29571_CommonData_PoC_ETRI_DoDo1.yaml` 의 `PacketLossRate`).
보내 주시는 값은 **퍼센트를 소수 한 자리로 적은 것**으로 보입니다. 1.7 % 라면 규격 값은 `17` 입니다.

UPF `8_` 의 `_packetLossRate`(같은 `PacketLossRate` 타입)도 같은 원천이라, 형식은 통과하지만 UE4 에서 `100` · `82` · `40` · `17` · `2`
처럼 **퍼센트를 올림한 정수**로 옵니다.

**원인 (9/28 소스 기준으로 추정).**
- 수집 서버가 손실률을 퍼센트 `%.1f` 로 DB 에 적재합니다(`nw_collect/collect_server/recv_server_db.c`).
- `Replace_Stamp_One()`(`src/ncof_flow_targeting.cpp:69`)이 그 문자열을 `@@UEn_LOSS@@` 자리에 그대로 넣습니다. 이 자리표시자는
  `9_`·`9p_`·`10_a`·`10p_a` 의 `plr` 네 필드와 `8_`·`8p_` 의 `_packetLossRate` 에 쓰입니다(예: `9_…tmpl:175-178`).
- 출력 정수화 목록 `Is_Ncof_Integer_Field_Local()`(`src/ncof_flow_common.cpp:816-848`)에는 `_packetLossRate` 만 있고
  `plr` 네 필드가 없어, `9_` 계열은 소수 그대로, `8_` 계열은 올림 정수로 나갑니다.

**요청.** DB 값은 그대로 두시고, **`Replace_Stamp_One()` 의 `@@…_LOSS@@` 치환에서 `round(값 × 10)` 한 0 ~ 1000 정수**를 넣어 주십시오
(1.7 % → `17`, 3.3 % → `33`, 100 % → `1000`). 그러면 위 여섯 템플릿이 한 번에 맞춰집니다.
- ⚠️ **정수화 목록에 `plr` 을 추가하는 것만으로는 부족합니다.** 그러면 올림 정수(1.7 → `2`)가 되어 형식 검증은 통과하지만
  값은 여전히 퍼센트라 규격상 0.2 % 로 읽힙니다(실제의 약 1/8). `_packetLossRate` 가 지금 이 상태입니다.
- 값이 없는 주기는 지금처럼 필드를 생략하시면 됩니다.

**여쭙는 것.**
1. 기동 직후 첫 주기(`8_` 19:46:33, `9_` 19:47:34, 둘 다 UE4)에 `100` 이 왔습니다. 같은 주기 `9_` 의 `thrputDl` 이 107.45 Mbps 라
   실제 100 % 손실로 보기는 어려운데, 측정 전 초기값인지요?
2. 관측값이 모두 n/60 을 퍼센트로 바꿔 소수 한 자리로 반올림한 값입니다(1/60 → 1.7, 2/60 → 3.3, 11/60 → 18.3, 46/60 → 76.7).
   손실률을 STAMP 프로브 60개(예: 60초 창) 기준으로 계산하시는지요?

저희는 지금 이 네 필드를 임시 보정 계층에서 반올림해 받고 있고, 이 때문에 보정 계층을 걷어 내지 못하고 있습니다.

## 4. 확인 요청 — QoS UDP(`192.168.1.182:26321`) 적용 여부

위 19:54:38 `14_e` 수신 뒤 SBI 로그에 아래와 같이 UDP 가 발사되었습니다.

```
QOS UDP send Success target=192.168.1.182:26321 size=128
QOS UE1 imsi=001010070000101 gbrDl=5.000000    mbrDl=10.000000
QOS UE2 imsi=001010070000103 gbrDl=500.000000  mbrDl=500.000000
QOS UE3 imsi=001010070000102 gbrDl=1000.000000 mbrDl=1000.000000
QOS UE4 imsi=001010070000104 gbrDl=500.000000  mbrDl=500.000000
```

19:56:38 에는 평시 값(UE2 · UE4 `1000/1000`, UE3 `0/0`)으로 다시 발사되었습니다. 그 사이 두 가지가 서로 다르게 보였습니다.

| 측정 | 19:54 | 19:55 | 19:56 | 19:57 |
|---|---|---|---|---|
| AF `9_` UE4(`192.168.104.10`) `thrputDl` | 107 Mbps | **32.2 Mbps** | **32.23 Mbps** | 106.73 Mbps |
| UPF client-2 `filter-002-dl`(`→192.168.102.10`) | (19:54:33 이상값) | 102.18 Mbps | 104.66 · 107.08 Mbps | — |

AF 측정값은 떨어졌다가 평시 값을 보낸 뒤 회복했지만, UPF 가 잡은 client-2 흐름은 그대로였습니다. AF 는 client-2 트래픽을
`192.168.104.10` 으로, UPF 는 `192.168.102.10` 으로 잡고 있고(UPF 의 `filter-004-dl`(`→192.168.104.10`)은 평소 약 0.0005 Mbps),
저희로서는 QoS 영향인지 측정 쪽 현상인지 판단하기 어려워 여쭙니다.

1. 26321 을 받는 쪽이 **UPF 이고, 받은 값을 실제 세션 QoS 에 적용**하는지요? 적용되었다면 그 시각의 적용 로그를 부탁드립니다.
2. **IMSI 체계.** UPF `8_` 는 `192.168.104.10` 을 `imsi-001010000000004`(102.10 은 `…003`, 103.10 은 `…002`)로 보고하는데,
   QoS UDP 에는 `001010070000101` ~ `…104` 가 실립니다. UPF 는 어느 IMSI 로 세션을 찾는지요? 번호 순서도 달라서(예: 102.10 은 UPF `…003`,
   QoS UE3 `…102`), 슬롯과 UE 의 대응을 알려 주시면 감사하겠습니다.
3. **단위.** 저희는 `"500.0 Mbps"` 처럼 보내는데 `std::stod` 에서 단위가 빠집니다. 다만 UE4 의 500 만으로는 32 Mbps 가 설명되지
   않습니다. 같은 시각 UE3(`…102`, client-2 의 gNB2 경로) 슬롯이 `0/0` → `1000/1000` 으로 바뀐 것이 client-2 트래픽의 경로 분배에
   영향을 주는지, 또는 단위 해석이 다른지 여쭙니다.
4. **`0` 의 의미와 유효기간.** 평시 UE3(`…102`) 는 `0/0` 인데 UPF `filter-002-dl`(`→192.168.102.10`)은 약 104 Mbps 입니다 —
   `0` 이 차단이라면 맞지 않습니다. 또 저희 `14_e` 에는 유효기간 60초(19:54:38 ~ 19:55:38)가 실렸는데 AF 저하는 19:56:38 에 평시 값을
   다시 보낸 뒤에야 풀렸습니다. `0` 이 무엇을 뜻하는지(차단 / 무제한 / 미적용), 적용 값이 언제까지 유지되고 어떻게 해제되는지 궁금합니다.

현재는 UDP 발사가 실패하거나 UE 4개가 다 차지 않아도 SBI 응답이 `200` 이라 저희 쪽에서는 적용 여부를 알 수 없습니다.
가능하시면 적용 결과를 로그로 남기시거나, 응답 본문에 발사 여부(예: `udp_sent`, `fill_count`)를 실어 주시면 좋겠습니다.

  60 이라 문제가 없지만, `repPeriod` 와 같은 값으로 치환해 주시면 좋겠습니다.
- **AF 성능값 결손.** `192.168.102.10` 의 `perfData` 가 매 주기 비어 오고, UE4 는 19:56:36 에 지연·손실 필드가 생략되었습니다.

- **`monDur` 고정값.** 12월 31일 12:00 에 같은 방식으로 만료됩니다. 1월 이후 시연을 위해 기동 시각 기준 상대값 방식을 검토해 주시면
  좋겠습니다.
