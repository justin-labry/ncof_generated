### 요청 1 (치명) — ISO8601 소수 초 파싱

**위치:** `src/ncof_flow_subscription_core.cpp:226`

```c
ret = sscanf(time_text.c_str(), "%d-%d-%dT%d:%d:%d%c%d:%d",
             &year, &mon, &day, &hour, &min, &sec, &tz_sign, &tz_hour, &tz_min);
if (ret < 6) { return 0; }
...
if (ret == 9) {                       // :246 — 타임존 보정
    offset_sec = (tz_hour * 3600) + (tz_min * 60);
```

**현상:** 시각 문자열에 소수 초가 있으면(`2026-09-10T22:31:26.057728+09:00`) `%c` 가 타임존 부호 대신
`.` 를 읽어 반환값이 9가 되지 못합니다. `if (ret < 6)` 은 통과하므로 파싱은 "성공" 처럼 보이지만
`:246` 의 타임존 보정이 건너뛰어져 **KST 벽시계 값을 UTC 로 간주**하게 됩니다.

**영향:** `targetPeriod.startTime` 이 정확히 +9시간 미래로 계산되어 스케줄러가 그 시각으로 예약합니다.
결과적으로 **UPF 계열 주기 리포트(`8_`)가 사실상 오지 않습니다.** NEF 통지 4종은 정상 수신되는데
UPF 계열만 0건이라는 증상으로 나타났습니다.

**규격 근거:** 3GPP TS 29.571 의 `DateTime` 은 RFC 3339 형식으로 소수 초를 허용합니다.

**요청:** 소수 초를 허용하도록 파싱을 보완해 주십시오. `sscanf` 를 유지하시려면 초 항목을 `%d`
대신 실수로 받거나, 소수부를 별도 필드로 흡수하는 형태가 간단합니다.

**현재 우회:** NCOF 가 발송 직전 `targetPeriod` 의 소수 초를 제거하고 있습니다
(`_DODO1_NO_FRACTIONAL_SECONDS`). 수정 반영 시 이 패치를 제거하고 재검증하겠습니다.

- `templates/send/13p_d_NncofEventsSubscriptionNotification_from_RICF_to_NCOF_v1.0_POWER.tmpl:8`

```
현재    "_powerEnergyConsInfos": [ ... ]
규격    "_powerEnergyConsumptionInfos": [ ... ]
```

**규격 근거:** 양측 합의 규격 `TS29591_Nnef_EventExposure_PoC_ETRI_DoDo1.yaml:498` 이 프로퍼티를
`_powerEnergyConsumptionInfos` 로 선언합니다. 내부의 `_powerEnergyConsData` 는 양측이 일치하므로

**영향:** 해당 스키마가 `additionalProperties: true` 이므로 **검증 오류 없이 조용히 드롭**됩니다.
그 결과 `_POWER_ENERGY_CONSUMPTION` 이벤트 본문이 통째로 사라져 NCOF 가 전력·에너지 소비 정보를
전혀 수신하지 못합니다. 오류가 나지 않기 때문에 가장 발견이 어려운 유형입니다.

**요청:** 위 템플릿 2개 파일의 키 이름을 `_powerEnergyConsumptionInfos` 로 수정해 주십시오.

### 요청 3 (높음) — throughput 값의 단위 접미사 누락

**위치:** `src/ncof_flow_report_common.cpp:527-531`

```c
// :524-525 — 정상 (따옴표 + 단위)
Replace_All(body, "__VAL_0_0_MBPS__",    Json_Quote("0.0 Mbps"));
Replace_All(body, "__VAL_1000_0_MBPS__", Json_Quote("1000.0 Mbps"));

// :527-531 — 같은 표 안에서 따옴표도 단위도 없는 생 정수
Replace_All(body, "__VAL_50_MBPS__",  "50000000");
Replace_All(body, "__VAL_150_MBPS__", "150000000");
```

**현상:** 같은 토큰 표 안에서 위쪽 두 줄은 `"0.0 Mbps"` 로 정상인데, `__VAL_*_MBPS__` 계열은
단위 없는 bps 정수로 치환됩니다. 국소적인 회귀로 보입니다.

**규격 근거:** TS 29.571 이 정의하는 세 타입 모두 **단위 접미사가 붙은 문자열**입니다
(`TS29571_CommonData_PoC_ETRI_DoDo1.yaml`):

| 타입 | 패턴 | 위치 |
|---|---|---|
| `BitRate` | `^\d+(\.\d+)? (bps\|Kbps\|Mbps\|Gbps\|Tbps)$` | `:4132` |
| `PacketRate` | `^\d+(\.\d+)? (pps\|kpps\|Mpps\|Gpps\|Tpps)$` | `:4148` |
| `Volume` | `^\d+(\.\d+)? (B\|kB\|MB\|GB\|TB)$` | `:4163` |

**영향:** NCOF 의 파서는 단위 접미사가 없는 값을 **Mbps 로 간주**합니다. 따라서
`150000000` 이 `150,000,000 Mbps` 로 해석되어 **10⁶배로 부풀려지고**, 임계값 판정이 항상
"고부하" 로 기울어 gNB2 전력 제어 판정이 오염됩니다.

**요청:** 값을 바꾸지 마시고 **기존 정수에 기본 단위만 붙여** 문자열로 치환해 주십시오.
단위 변환이 없어 무손실이고 반올림 문제도 생기지 않습니다.

```c
Replace_All(body, "__VAL_150_MBPS__", Json_Quote("150000000 bps"));   // BitRate
Replace_All(body, "__VAL_500_KPPS__", Json_Quote("500000 pps"));      // PacketRate
Replace_All(body, "__VAL_9_GB__",     Json_Quote("9000000000 B"));    // Volume
```

> 단위 접두어를 쓰실 경우 규격 표기가 `kpps`·`kB` 로 **소문자 k** 이고 `Kbps` 는 대문자 K 라는
> 점만 주의해 주십시오. Mbps 텍스트를 선호하시면 같은 파일 `:909` 의
> `Json_Bps_To_Mbps_Text()` 가 이미 `"150 Mbps"` 형식을 만들고 있어 재사용 가능합니다
> (다만 이 헬퍼는 무효 시 `-999` 를 반환하므로 아래 후속 항목 2번과 함께 검토가 필요합니다).

**현재 우회:** NCOF 가 수신 시 단위를 붙여 정규화하고 있습니다(관대 수신 계층). 수정 반영 시
이 계층의 상당 부분을 제거할 수 있습니다.

### 요청 4 (낮음 · 조건부) — 구독 응답의 구독 ID

**위치:** `src/http2_server.cpp:78-85`, `:257-271`

**현상:** 하위 NF 구독 성공 응답이 `200` + `{"result":"ok"}` 이고, 본문·헤더·`Location`
어디에도 구독 ID 가 없습니다.

**규격 근거:** 3GPP SBI 의 구독 생성은 생성된 리소스 식별자를 반환하는 것이 원칙입니다.

**요청:** uuid 를 발급해 **`Subscription-ID` 응답 헤더**로 실어 주십시오. 본문 구조는 바꾸지
않아도 됩니다.

> 🔴 **함께 반영해 주셔야 하는 조건이 있습니다.** 현재 두두원은 요청 본문의 `notifId` 를 자신의
> `subscription_id` 로 채택하고(`ncof_flow_subscription_handlers.cpp:53-54` 등), 구독 해지 시
> `key` / `subscription_id` / `notif_id` 중 하나와 매칭합니다
> (`ncof_flow_subscription_core.cpp:1209`).
>
> NCOF 는 응답에 ID 가 있으면 **그것을 우선 사용**하므로, 새로 발급한 uuid 를 헤더로만 돌려주고
> 내부 식별자를 `notifId` 로 두시면 **NCOF 의 구독 해지가 404 로 실패**합니다.
> 발급한 uuid 를 `sub.subscription_id` 에 저장하고 **해지 매칭 대상에 포함**해 주십시오.

**우선순위를 낮게 둔 이유:** 이 항목은 NCOF 측에서 자체 해소했습니다. 응답에 ID 가 없으면
요청 본문의 `notifId` 를 하위 구독 ID 로 채택하도록 보완했고, 실장비 대상 구독 해지 10건이
전부 `200 OK` 로 성공하는 것을 확인했습니다. 따라서 **연동을 막는 사안은 아니며**, 규격 준수
차원의 개선 요청으로 이해해 주시면 됩니다.

### 참고 — 후속으로 정리해 보낼 사항

아래는 이번 요청에 포함하지 않았습니다. 우리 쪽 참조 샘플도 함께 손봐야 하는 항목이라
정리 후 별도로 안내드리겠습니다.

1. **`13p_d` 계열의 구조 항목 5종** — 현재 이 통지는 NCOF 스키마 검증에서 거절되고 있습니다.
   일부는 2026-05-26 규격 갱신(`_nodeAddrs` 등) 반영 요청에 해당하고, 일부는 우리 샘플도
   위반 중이라 양측을 함께 맞춰야 합니다.
2. **`-999` 센티넬** — 값이 없을 때 필드를 생략하는 것이 규격입니다. 3GPP 타입에 "데이터 없음"
   표현이 없어(`PacketDelBudget` 은 min 1, `PacketLossRate` 는 0..1000 등) `-999` 가 타입 위반이
   됩니다. 요청 3의 헬퍼(`Json_Bps_To_Mbps_Text`)도 무효 시 `-999` 를 반환하므로 함께 논의가
   필요합니다.
3. **`validityTimes` 위치** — 규격과 현재 회선의 위치가 다릅니다. 어느 한쪽만 옮기면 두두원의
   UPF 구독 시간창 검증이 조용히 깨지므로 **동시 수정**이 필요합니다.
