### 요청 1 (치명) — ISO8601 소수 초 파싱

**위치:** `src/ncof_flow_subscription_core.cpp:226`

```c
ret = sscanf(time_text.c_str(), "%d-%d-%dT%d:%d:%d%c%d:%d",
             &year, &mon, &day, &hour, &min, &sec, &tz_sign, &tz_hour, &tz_min);
if (ret < 6) { return 0; }                    // :227
...
if (ret == 9) {                               // :246 — 타임존 보정
    offset_sec = (tz_hour * 3600) + (tz_min * 60);
```

**현상:** 시각 문자열에 소수 초가 있으면(`2026-09-10T22:31:26.057728+09:00`) `%c` 가 타임존 부호 대신
`.` 를 읽고, 이어지는 `%d` 가 소수부(`057728`)를 삼킨 뒤 포맷의 `:` 리터럴이 `+` 와 어긋나 **반환값이 8**
이 됩니다. `if (ret < 6)` 은 통과하므로 파싱은 "성공" 처럼 보이지만, `:246` 의 타임존 보정이 건너뛰어져
`timegm()`(`:240`)이 **KST 벽시계 값을 UTC 로 간주**하게 됩니다. 저희 쪽에서 같은 코드로 재현해
epoch 이 정확히 `+32400`초 어긋나는 것을 확인했습니다.

**영향 (우회 패치 적용 전, 2026-09-09 실측):** `targetPeriod.startTime` 이 정확히 +9시간 미래로 계산되어
스케줄러가 그 시각을 다음 전송 시각으로 예약합니다(`:1057-1059`). 그 결과 감시 창 안에서
**UPF 계열 주기 리포트가 사실상 수신되지 않았습니다** — 구독 3/3p 의 `8_`·`8p_` 템플릿과
구독 7/7p 의 `12_c`·`12p_c` 템플릿이 모두 해당됩니다(`start_epoch` 을 이 파서로 채우는 핸들러가
`ncof_flow_subscription_handlers.cpp:140` 과 `:717` 두 곳입니다). NEF 통지는 정상 수신되는데
UPF 계열만 0건이라는 증상으로 나타났습니다.

**현 상태:** 9월 9일 밤 NCOF 측에 우회 패치를 적용한 뒤로는 정상 수신되고 있습니다. 따라서 **지금
장비를 확인하시면 이 증상은 재현되지 않습니다.** 근본 원인은 그대로 남아 있습니다.

**규격 근거:** TS 29.571 의 `DateTime` 은 OpenAPI `format: date-time`(RFC 3339)이며 소수 초를 허용합니다.

**요청:** 소수 초를 허용하도록 파싱을 보완해 주십시오. 현재의 `sscanf` 구조를 유지하신다면
**초 항목만 실수로 받는 방식**이 가장 간단하고 안전합니다.

```c
double sec_d = 0.0;
ret = sscanf(time_text.c_str(), "%d-%d-%dT%d:%d:%lf%c%d:%d",
             &year, &mon, &day, &hour, &min, &sec_d, &tz_sign, &tz_hour, &tz_min);
...
tm_value.tm_sec = (int)sec_d;   // 소수부 절삭
```

이렇게 두시면 소수 초가 있는 `…:26.057728+09:00` 과 없는 `…:26+09:00` **양쪽 모두 반환값이 9** 가 되어
`:246` 의 보정이 그대로 적용됩니다(저희 쪽에서 동일 코드로 재현 확인했습니다).

> ⚠️ 소수부를 `%d` 같은 **별도 필드로 받는 방식은 권하지 않습니다.** 소수 초가 *없는* 입력에서는
> 포맷의 `.` 매칭이 깨져 반환값이 6 으로 떨어지고, 이번에는 반대로 소수 초가 없는 입력에서 보정이
> 건너뛰어집니다. 현재 NCOF 는 우회 패치로 소수 초를 **제거한** 시각을 보내고 있어, 이 방식으로
> 수정하시면 배포 직후 지금 정상인 경로가 오히려 깨집니다.

**회귀 확인 범위:** 같은 파서가 `expiry`·`monDur`·`validityTimes` 의 시간창 검증에도 쓰입니다
(`:272`, `:345`, `:374`, `:398`, `:593`). 수정 후 이 경로들도 함께 확인해 주시면 좋겠습니다.

**현재 우회:** NCOF 가 발송 직전 `targetPeriod` 의 소수 초를 제거하고 있습니다
(`_DODO1_NO_FRACTIONAL_SECONDS`). 수정 반영 시 해제하고 재검증하겠습니다.

### 요청 2 (치명) — `13p_d` 통지가 NCOF 스키마 검증에서 전량 거절되고 있습니다

먼저 현 상태를 정확히 공유드립니다. **`13p_d` 통지는 현재 100% 거절되고 있습니다.**

함께 실려 오므로 **두 이벤트가 함께 유실**되고 있습니다.

원인은 네 가지이고, 아래 ①~④ 를 **한 묶음으로** 반영해 주셔야 통지가 통과합니다.

#### ① 전력 배열의 키 이름

**위치:** `templates/send/13p_d_…_v1.0.tmpl:117`, `templates/send/13p_d_…_v1.0_POWER.tmpl:8`

```
현재    "_powerEnergyConsInfos": [ ... ]
규격    "_powerEnergyConsumptionInfos": [ ... ]
```

배열 원소 내부의 `_powerEnergyConsData` 이하 키는 양측이 이미 일치하므로 안쪽은 손대실 필요가 없습니다.

**성격:** 이 항목만은 **오류를 내지 않습니다.** 규격에 없는 이름이라 수신 모델이 미지의 속성으로 보고
조용히 버리기 때문입니다. 그래서 위 8건의 오류 목록에는 나타나지 않지만, ②~④ 를 고쳐 통지가 통과하게

#### ② 이벤트 시각 필드의 표기 — `timestamp` → `timeStamp`

**현재:** `eventNotifs[].timestamp` (소문자 s) · **규격:** `eventNotifs[].timeStamp` — **필수 필드**입니다

422 입니다. 값 형식 자체는 정상이므로 **키 이름만** 바꾸시면 됩니다.

> 🙏 이 항목은 **저희가 드린 참조 샘플(`13p_d` 예시 JSON)도 같은 소문자 표기를 쓰고 있습니다.**
> 저희 쪽 샘플을 먼저 정정해 함께 보내드리겠습니다. 혼선을 드려 죄송합니다.

#### ③ `_nodeAddrs` 의 구조 — 배열 → 단일 객체

**현재:** `"_nodeAddrs": [ { … } ]` · **규격:** `$ref: AddrFqdn` — **단일 객체**입니다

위 8건 중 **2건**이 이 항목입니다(`_RF_SIGNAL` 과 `_POWER_ENERGY_CONSUMPTION` 양쪽).

**이 건은 저희 쪽에 원인이 있습니다.** 처음 드린 참조 샘플에 이 필드가 배열로 들어 있었고,
저희가 **2026-05-26 에 단일 객체로 정정**했습니다(`13p_d` 예시 JSON 4곳). 그 이전 사본을 기준으로
구현하신 것으로 보입니다. 혼선을 드려 죄송합니다.

현재 규격 스키마와 참조 샘플이 양쪽 모두 단일 객체이므로, 이에 맞춰 수정 부탁드립니다.

#### ④ `nrLocation` 의 필수 필드와 셀 ID 형식

**현재:** `_loc.nrLocation` 에 `tai` 가 없고, UE1 항목에는 `ncgi` 도 없습니다. `ncgi.nrCellId` 값은 `"cell-002"` 입니다.
**규격:** `NrLocation.required: [ncgi, tai]` 이고, `nrCellId` 는 `^[A-Fa-f0-9]{9}$` — 36비트를 hex 9자리로
표기합니다(TS 38.413 §9.3.1.7). 위 8건 중 **3건**(`tai` 2 · `ncgi` 1)이 누락, **1건**이 `nrCellId` 형식입니다.

`tai`·`ncgi` 는 값을 저희가 지어낼 수 없어 관대 수신으로도 보정이 불가능합니다.
동일 이유로 `"cell-002"` 에서 올바른 hex 를 유도할 근거도 없습니다.

> 🙏 `nrCellId` 형식 역시 **저희 참조 샘플이 아직 `cell-001`/`cell-002` 로 되어 있습니다.**
> ② 와 함께 정정본을 보내드리겠습니다. `tai`·`ncgi` 는 저희 샘플에서 이미 정정되어 있습니다.

#### 요청 요약

①~④ 를 함께 반영해 주십시오. **①만 반영하시면 전력 블록이 처음으로 검증 대상에 올라오면서
오류가 8건에서 14건으로 오히려 늘어납니다**(전력 블록도 ③·④ 의 제약을 동일하게 받습니다).
②~④ 만 반영하시면 통지는 통과하지만 전력·에너지 데이터가 비어 있게 됩니다.

②·④ 의 저희 쪽 샘플 정정본은 별도로 보내드리겠으니, **하나의 `13p_d` 작업 묶음**으로 잡아 주시면
재작업이 없으실 것입니다.

### 요청 3 (높음) — throughput·packet rate·volume 값의 단위 접미사 누락

**위치:** `src/ncof_flow_report_common.cpp:527-539` (`Apply_Ncof_Common_Template_Values()`, `:411`)

따옴표·단위 없이 생 정수로 치환되는 토큰이 **총 11개**입니다.

```c
// :524-525 — 정상 (따옴표 + 단위)
Replace_All(body, "__VAL_0_0_MBPS__",    Json_Quote("0.0 Mbps"));
Replace_All(body, "__VAL_1000_0_MBPS__", Json_Quote("1000.0 Mbps"));

// :527-531 — BitRate 계열 5개
Replace_All(body, "__VAL_50_MBPS__",  "50000000");
Replace_All(body, "__VAL_100_MBPS__", "100000000");
Replace_All(body, "__VAL_150_MBPS__", "150000000");
Replace_All(body, "__VAL_200_MBPS__", "200000000");
Replace_All(body, "__VAL_300_MBPS__", "300000000");

// :533-536 — PacketRate 계열 4개 (__VAL_50_KPPS__ … __VAL_500_KPPS__)
// :538-539 — TrafficVolume 계열 2개 (__VAL_3_GB__, __VAL_9_GB__)
```

**현상:** 같은 소스 안에 **동일한 토큰명을 쓰는 표가 두 벌** 있고 표기 기준이 서로 다릅니다.
`src/ncof_send_templates.cpp:272-285` 는 같은 토큰들을 `"50 Mbps"`·`"500 kpps"`·`"9 GB"` 처럼
**단위가 붙은 문자열**로 정의하고 있습니다(`Add_String_Token` 이 `:142` 에서 JSON 문자열로 감쌉니다).
두 경로가 모두 활성이라, 한 메시지 안에 `"dlAvailableBitrate": "200 Mbps"` 와
`"dlAverageThroughput": 150000000` 이 함께 담겨 전달됩니다.

**규격 근거:** TS 29.571 이 정의하는 세 타입 모두 **단위 접미사가 붙은 문자열**입니다
(`TS29571_CommonData_PoC_ETRI_DoDo1.yaml`):

| 타입 | 패턴 | 위치 |
|---|---|---|
| `BitRate` | `^\d+(\.\d+)? (bps\|Kbps\|Mbps\|Gbps\|Tbps)$` | `:4132` |
| `PacketRate` | `^\d+(\.\d+)? (pps\|kpps\|Mpps\|Gpps\|Tpps)$` | `:4148` |
| `TrafficVolume` | `^\d+(\.\d+)? (B\|kB\|MB\|GB\|TB)$` | `:4163` |

**영향:** NCOF 의 파서는 단위 접미사가 없는 값을 Mbps 로 간주합니다. `150000000` 이
`150,000,000 Mbps` 로 해석되어 **10⁶배로 부풀려지고**, 임계값 판정이 항상 "고부하" 로 기울어
gNB2 전력 제어 판정이 오염됩니다. UL 계열(`ulAverageThroughput` 등)도 동일합니다.

**요청:** 값을 바꾸지 마시고 **기존 정수에 기본 단위만 붙여** 문자열로 치환해 주십시오.
단위 변환이 없어 무손실이고 반올림 문제도 생기지 않습니다.

```c
Replace_All(body, "__VAL_150_MBPS__", Json_Quote("150000000 bps"));   // BitRate
Replace_All(body, "__VAL_500_KPPS__", Json_Quote("500000 pps"));      // PacketRate
Replace_All(body, "__VAL_9_GB__",     Json_Quote("9000000000 B"));    // TrafficVolume
```

세 계열이 같은 템플릿(`8_`·`8p_`·`12_c`·`12p_c`) 안에서 함께 쓰이므로 **11개를 함께** 반영해 주십시오.
`:524-525` 두 줄은 이미 정상이라 그대로 두시면 됩니다. `ncof_send_templates.cpp` 쪽 표기를 기준으로
맞추시는 것이 가장 간단할 것 같습니다.

> 단위 접두어를 쓰실 경우 규격 표기가 `kpps`·`kB` 는 **소문자 k**, `Kbps` 는 **대문자 K** 라는 점만
> 주의해 주십시오.
>
> 참고로 현재 회선의 throughput 값이 템플릿 상수라는 점은 저희도 인지하고 있습니다. 단위 접미사만
> 정정되면 실측값으로 전환하실 때도 그대로 동작합니다.

**현재 우회:** NCOF 가 수신 시 단위를 붙여 정규화하고 있습니다. 수정 반영 시 이 계층의 상당 부분을
제거할 수 있습니다.

### 요청 4 (중간) — 제어 명령의 실제 반영 여부를 확인할 수단

현재 NCOF 가 확보할 수 있는 근거는 **제어 명령에 대한 `HTTP 200` 까지**입니다. 그 200 이 gNB2 의
실제 제어 성공을 뜻하지는 않는 것으로 보입니다.

- `src/ncof_flow_control.cpp:320` 의 `save_count++` 가 `:324` 의 gNB2 SSH 호출보다 **먼저** 실행됩니다.
- `src/gnb_ssh_control.cpp:116-121` 은 SSH 셸아웃 실패 시 로그만 남기고 `0` 을 반환합니다.

즉 `eu.gnbControl.py cell-stop` 이 실패해도 NCOF 는 `200` 을 받습니다. 또한 수신한 제어 명령은
MySQL 에만 기록되고 `send_json/` 에도 남지 않아, 저희 쪽에서는 **명령이 수용되었는지조차 확인할 수
없습니다.** 통지 본문의 `_powerState` 도 템플릿 고정값(`"ACTIVE"`)이라 적용 결과가 되돌아오지 않습니다.

**요청 — 아래 중 하나만 해 주셔도 종단 검증을 마무리할 수 있습니다.**

1. **(가장 간단)** 최근 제어 명령 수신 시점의 `sbi_poc_app` stderr 에서 `gnb_ssh_control` 관련 로그와
   제어 직후 셀 상태를 한 번만 공유해 주십시오.
2. 수신한 제어 명령을 `send_json/` 처럼 파일로 한 건이라도 남겨 주십시오(수신 덤프).
3. SSH 셸아웃 실패를 HTTP 응답 코드에 반영해 주십시오 — 실패 시 `500`. 그러면 NCOF 가 스스로 판별합니다.
4. 통지의 `_powerState` 에 **실제 적용 상태**를 실어 주십시오. 그러면 NCOF 가 폐루프를 자체 검증할 수 있습니다.

1번은 이번 회신에, 2~4번은 여유 있으실 때 검토해 주시면 감사하겠습니다.

### 협의 5 (낮음 · 지금 수정 요청 아님) — 구독 응답의 구독 ID

하위 NF 구독 성공 응답이 `200` + `{"result":"ok"}` 이고, 본문·헤더 어디에도 구독 ID 가 없습니다
(`src/http2_server.cpp:364-386` POST 분기, `:78-85` 본문 생성, `:270-272` HTTP/2 응답 헤더,
`:860-864` HTTP/1.1 응답 헤더).

**이 항목은 NCOF 측에서 자체 해소했습니다.** 응답에 ID 가 없으면 요청 본문의 `notifId` 를 하위 구독
ID 로 채택하도록 보완했고, 실장비 대상 구독 해지 10건이 전부 `200 OK` 로 성공하는 것을 확인했습니다.
그래서 **지금은 수정을 요청드리지 않습니다.**

> 🔴 **다만 한 가지만 미리 부탁드립니다.** 구독 식별자 처리를 바꾸시게 되면 **배포 전에 알려 주십시오.**
>
> 현재 두두원은 요청 본문의 `notifId` 를 자신의 `subscription_id` 로 채택하고
> (`ncof_flow_subscription_handlers.cpp:53`·`:212`·`:354`·`:447`·`:604`·`:682` 6곳),
> DELETE 시 `key`/`subscription_id`/`notif_id` 중 하나와 매칭합니다(`ncof_flow_subscription_core.cpp:1209`).
> NCOF 의 해지는 이 동작에 의존하고 있습니다.
>
> 만약 새 식별자를 발급해 응답으로만 돌려주시고 내부 식별자를 `notifId` 로 두시면, NCOF 가 보내는
> DELETE 가 매칭되지 않습니다. **그런데 NCOF 는 `404` 를 "이미 해지된 구독" 으로 간주해 성공으로
> 처리하고 자기 기록까지 지웁니다.** 그러면 NCOF 로그에는 실패 흔적이 남지 않고 **두두원 쪽 구독만
> 살아남아 주기 리포트가 계속 전송**되는 형태가 됩니다. 양쪽 모두 오류가 보이지 않아 발견이 매우
> 어렵습니다. 저희 쪽 `404` 처리도 함께 손보겠습니다.

규격 정합화를 진행하실 때를 위해 참고로 적어 둡니다. 양측 합의 규격은 구독 생성 성공 응답을
**`201 Created` + 필수 `Location` 헤더**로 규정하고 있습니다
(`TS29591_Nnef_EventExposure_PoC_ETRI_DoDo1.yaml:44-58`, `TS29508_Nsmf_EventExposure_PoC_ETRI_DoDo1.yaml:43-53`).
`src/http2_server.cpp:284-297` 에 `201` 을 반환하는 `handle_subscription_request()` 가 이미 작성되어
있는 것으로 보이나 현재 호출되지는 않는 듯합니다. 다만 **NCOF 쪽도 아직 `Location` 헤더를 읽지
않으므로**, 이 항목은 반영하시더라도 저희 수정과 시점을 맞춰야 합니다. 서두르지 않으셔도 됩니다.

### 참고 — 후속으로 정리해 보낼 사항

아래는 이번 요청에 포함하지 않았습니다. 저희 쪽 참조 샘플도 함께 손봐야 하거나 양측 동시 수정이
필요한 항목이라, 정리 후 별도로 안내드리겠습니다.

1. **`-999` 센티넬** — 값이 없을 때는 필드를 생략하는 것이 규격입니다. 3GPP 타입에 "데이터 없음"
   표현이 없어(`PacketDelBudget` 은 최소 1, `PacketLossRate` 는 0..1000 등) `-999` 가 타입 또는 패턴
   위반이 됩니다. 실측상 UPF 통지 3,206건 중 1,863건이 `"dlAverageThroughput": "-999"` 를 담고 있어
   요청 3 과 함께 판정에 영향을 주고 있습니다. 요청 3 의 헬퍼(`Json_Bps_To_Mbps_Text`, `:909`)도
   무효 시 `-999` 를 반환하므로 함께 논의가 필요합니다.
2. **정수 필드의 소수값** — `pdb: 0.45`, `_dlMaxPacketDelay: 20.74` 등. 요청 3 과 같은 렌더링 계층 항목입니다.
3. **`validityTimes` 의 JSON 경로** — 합의 규격(`TS29564_Nupf_EventExposure_PoC_ETRI_DoDo1.yaml`)은
   이 필드를 `eventSubs[].upfEvents[].skipReportingInstruction.validityTimes` 에 두고 NCOF 도 그 경로로
   보내고 있으나, 두두원 구현은 한 단계 위인 `eventSubs[].upfEvents[].validityTimes` 를 조회하고 있어
   (`ncof_flow_subscription_core.cpp:496`·`641`·`696`) 시간창 검증에서 항상 건너뛰어집니다.
   **원인은 저희가 드린 예시 JSON 이 옛 평면 구조로 남아 있는 데 있습니다.** 예시를 정정한 뒤
   정확한 경로와 함께 안내드리겠으며, **한쪽만 옮기면 검증이 조용히 깨지므로 동시 수정이 필요합니다.**
