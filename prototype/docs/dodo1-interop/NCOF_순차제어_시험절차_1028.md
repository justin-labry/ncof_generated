## 1. 무엇이 바뀌나 (NCOF)

- **순서**: gNB2 ON = 15f ACTIVE → 200 → 14_e 분산 비율, OFF = 14_e 0:100 → 200 → 15f DEEP_SLEEP(10/26 회신 그대로). 순서는 목표 상태로 정한다 — 재기동 직후 첫 판정도 같다.
- **실패**: 앞 요청이 500 · 연결 오류 · 5초 타임아웃이면 뒤 요청은 보내지 않고, 이번 묶음 전부(성공한 앞 요청 포함)를 다음 **판정 틱(리더 틱, 약 20초)** 에 처음부터 다시 보낸다. 한 단계가 하나도 성공 못 하면 묶음 밖 구독의 전달 기록도 지운다(두두원 앱이 다시 떴을 수 있다) — 단계만 바뀐 14_e 가 실패해도 다시 보낼 때는 ON 이면 15f ACTIVE → 14_e 부터.
- **끼어들기 없음**: 한 묶음이 응답을 기다리는 동안 다른 틱은 보내지 않는다. 한 단계 상한 20초.
- **같은 NF 구독이 둘 이상**(고아 상향 트리)이면 그중 하나라도 성공하면 다음 단계로 간다(겹침 경고 로그). 겹친 것 중 실패한 것만 남은 단계도, 같은 NF 의 다른 구독이 이미 그 상태를 받았으면 넘어간다(「겹친 구독만 실패」 로그).
- **새 상향 구독이 들어오면**(두두원 앱 재기동 · 재구독) 남은 구독의 전달 기록을 지우고 다음 틱에 처음부터 순서대로 다시 보낸다(`새 상향 구독 — 남은 구독 N건(…)의 전달 기록을 지움` 로그 — 지울 기록이 있을 때만, 앞 실패로 이미 지워졌으면 안 찍힌다). 앱만 재기동해 옛 구독이 고아로 남아도 새 PCF 에 14_e 가 15f ACTIVE 보다 먼저 나가지 않는다 — 옛 RICF 구독의 15f 도 같은 :55556 의 새 앱에 닿고, 새 앱이 옛 subscriptionId 를 거절하면 그 단계가 실패해 새 RICF 가 붙어 15f 200 을 받을 때까지 14_e 를 보내지 않는다. 새 PCF 구독은 하위 구독 · 화면 연출(약 4초) 뒤에 붙는데, 옛 앱이 내려가 있는 동안 실패한 재시도가 그 사이 옛 PCF 구독으로 나가도 위 「실패」 규칙으로 15f 부터 간다. 남은 틈: ① RICF 구독이 하나도 없을 때(`RICF 구독이 없어 15f ACTIVE 확인 없이 14_e 만 보낸다` 경고) ② 새 앱이 뜬 뒤 새 PCF 구독이 붙기까지 약 5초 안에 실패 없이 판정이 바뀔 때 — 새 앱의 12p_c 는 새 구독이 붙어야 판정에 쓰이므로 사실상 없다.

추출(읽기만 — 콘솔은 밀리초, app.log 는 초라 순서를 못 가린다. 50MB 는 약 2.8시간분 — 재기동 직후 시험이면 충분하고, 더 지났으면 `tail -c` 를 늘리거나 `cat` 으로 새 런 전체를 넘긴다):
```bash
tail -c 50000000 /home/labry/git/ncof_generated/prototype/nncof-server/logs/console.<새 런>.log | python3 -I /home/labry/git/ncof_generated/prototype/docs/dodo1-interop/tools/seq_check.py --two
```
```bash
tail -c 5000000 /home/labry/git/ncof_generated/prototype/nncof-server/logs/console.<새 런>.log | sed 's/\x1b\[[0-9;]*m//g' | grep -a -E 'AI 분석 결과|순차 제어|HTTP Request: POST http://10.254.173.46:5555[56]|제어명령 실패|제어명령 전송 중 오류|CELL_POWER_STATE|GBR_DL' | cut -c1-200 | tail -40
```

**T1 ON**(DS → ACTIVE, 또는 재기동 첫 판정 ACTIVE):
1. `AI 분석 결과: gNB2 ACTIVE · … → 구독 2건 순차 전송 (RICF:…, PCF:…)` — RICF 가 앞
2. `CELL_POWER_STATE: ACTIVE` → `POST http://10.254.173.46:55556/ "HTTP/2 200 OK"` → `순차 제어 1/2 RICF 성공 응답 확인 → PCF`
3. `GBR_DL` 4줄 → `POST …:55555/ "HTTP/2 200 OK"` → `순차 제어 2/2 PCF 성공 응답 확인 — 완료`
- [ ] `seq_check.py` PASS. 15f 200 과 14_e 본문 사이는 수십 ms(0.5초 공백 없음). 전환 전체 약 0.3 ~ 0.4초.
- [ ] 두두원 로그(시각 없음 — 줄 순서): 15f 블록(`_CELL_POWER_CTRL notification received` … `network status gNB2 state=ACTIVE`)이 14_e 블록(`14_e QOS UE1 …` · `QOS UDP send Success` · `14_e qos assist set count=4`)보다 앞, 섞이지 않음.

**T2 OFF**(ACTIVE → DS): 1 `… DEEP_SLEEP · gNB2:WLAN 0:1000 … → 구독 2건 순차 전송 (PCF:…, RICF:…)` — PCF 가 앞 → `GBR_DL` 300 / 700 / **0** / 1000 → `:55555 200` → `순차 제어 1/2 PCF 성공 응답 확인 → RICF` → `CELL_POWER_STATE: DEEP_SLEEP` → `:55556 200` → `2/2 … 완료`.
- [ ] PASS. 두두원 로그에서 14_e 블록이 15f(DEEP_SLEEP) 블록보다 앞.

**T3 단계만 바뀜**(대부분의 틱): `… → 구독 1건 순차 전송 (PCF:…)` → `:55555 200` → `순차 제어 1/1 PCF 성공 응답 확인 — 완료`. 15f 없음.

`seq_check.py` 판정 뜻: `PASS` 순서 · 앞 200 뒤 뒤 출발 / `STOP(앞 실패 → 뒤 안 보냄)` 약속대로 멈춤 / `PASS(순서) · 뒤 실패 → 다음 판정 틱에 처음부터` 뒤 단계 실패 / `1건` 14_e 만 / `동시` 되돌리기 스위치 0 / `FAIL(…)` 약속 위반 — 이것이 나오면 멈추고 로그를 남긴다.

**T4 실패**(관측되면 — 실장비에서 일부러 만들 수는 없다):
- `제어명령 실패 … status_code: 500` 또는 `제어명령 전송 중 오류 발생: ReadTimeout … (http://10.254.173.46:5555x/)`
- 바로 `순차 제어 1/2 <앞> 실패 — <뒤> 는 보내지 않음, 다음 판정 틱에 처음부터 다시 보냄` · 그 묶음에 뒤 포트 POST 없음(`seq_check.py` STOP)
- 다음 리더 판정 틱(약 20초 뒤)에 **앞 대상부터** 다시(ON 이면 15f ACTIVE 를 또 보낸다 — 약속대로). 단계만 바뀐 14_e(T3)가 실패한 때도 다음에는 `구독 2건 순차 전송 (RICF:…, PCF:…)` — 하나도 성공 못 하면 모든 구독의 전달 기록을 지운다.
- 타임아웃이면 두두원은 이미 처리했을 수 있다(두두원 로그 확인 — 같은 요청이 두 번 처리돼도 무해: UPF 는 같은 비율, network_status 는 UPDATE 만).

자연 ON/OFF 가 드물다(10/27 DS 8회, 모두 한 틱). 확정 시험 지점은 재기동 직후 첫 판정이다. 전환을 일부러 만들려면(사용자 승인 · 두두원 사전 공유) `GNB2_LEVEL_BOUNDS_MBPS` 를 `sed -i` 로 잠깐 바꾼다 — **저장 즉시 다음 틱에 실 UPF 로 나간다**. 끝나면 `172,305,338` 으로 되돌린다.

## 6. 중단 · 되돌리기

- 중단 기준: `순차 제어 … 실패` 가 판정 주기 3번(약 1분) 넘게 이어짐 → 두두원에 원인(두두원 stderr 로그) 문의. 15f · 14_e 가 5초 타임아웃으로 반복 → 실제 SSH 가 켜졌는지부터 확인.

  ```bash
  sed -i 's/^GNB2_CONTROL_SEQUENTIAL=1$/GNB2_CONTROL_SEQUENTIAL=0/' /home/labry/git/ncof_generated/prototype/ncof_setting.conf
  ```
  다음에 실제로 보낼 것이 생긴 틱에 `제어 순서 설정 변경: 순차 → 동시 전송` 과 `… 동시 전송` 이 찍힌다. 편집기로 conf 를 저장하지 않는다(저장 도중 잘린 파일을 판정 틱이 읽으면 다른 GNB2_* 가 기본값으로 바뀌어 실 UPF 로 나갈 수 있다). 환경변수로는 안 바뀐다.

## 7. 두두원에 미리 알릴 것

- NCOF 재기동 시각, 그리고 재기동 뒤 첫 판정 때 15f · 14_e 를 순서대로 보낸다. 청소 후 재기동(4절 A)은 NCOF 가 두 번 뜨므로(A5 · A9) A6 ~ A7 사이에도 판정이 나면 한 번 더 — 최대 2회(실 UPF UDP 최대 2회).
- 앱만 재기동하면(청소 없이) NCOF 는 남은 옛 구독으로도 지금 상태를 약속한 순서로(ON 이면 15f → 14_e, OFF 면 14_e → 15f) 다시 보낸다(옛 subscriptionId) — 재기동 직후 전체 묶음 1 ~ 2번, 그 뒤로는 같은 제어가 겹친 구독마다 한 번씩 더. 새 빌드가 subscriptionId 를 검사해 거절해도 순서는 지켜지지만, 겹친 구독은 청소 후 재기동으로 정리한다.
- 실패하면 다음 판정 주기(약 20초)에 처음부터 다시 보낸다 — ON 이면 15f ACTIVE 부터(단계만 바뀐 14_e 가 실패한 때도). 계속 500 이면 20초마다 반복.
- NCOF 응답 대기는 5초다 — 더 늦은 응답은 실패로 보고 다시 보낸다(두두원은 이미 처리했을 수 있다).
- 앱 재기동은 NCOF 와 시각을 맞춰 주실 것(겹친 상향 구독 방지).
