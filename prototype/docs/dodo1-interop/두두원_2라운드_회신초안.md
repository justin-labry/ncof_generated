## 2. UDP 목적지에 수신 리스너가 관측되지 않았습니다

위 발사는 확인되었으나, 목적지 `192.168.1.182:5555` 에서 **UDP 리스너를 찾지 못했습니다.**
**9/18 21시경** `ss -lun` 확인 시점에 해당 포트가 없었고 PFCP(8805/8806)만 떠 있었습니다.
(저희가 이해하기로 `192.168.1.182` 는 두두원 서버 자신의 `enp131s0f0` 주소로 보입니다.)

UDP `sendto()` 는 수신자가 없어도 성공을 반환하므로, `QOS UDP send Success` 로그만으로는
**실제 수신 여부를 구분할 수 없습니다.**

1. `192.168.1.182:5555` 에서 수신하는 프로세스가 **별도로 기동되어야 하는 것인지**,
   아니면 상시 동작해야 하는데 내려가 있던 상태인지
2. 수신 측이 이 128바이트 패킷을 받아 **실제로 QoS 를 적용**하는지 확인할 방법이 있는지
   (적용 후 로그 한 줄이면 충분합니다)
3. 지난 회신에서 여쭌 항목을 한 번만 더 올립니다 — **UDP 전송(또는 gNB2 SSH)이 실패했을 때
   SBI 응답을 `500` 으로 내려 주실 수 있는지**입니다. 지금은 두 경로 모두 실패해도 NCOF 가 받는
   응답이 `200` 이라, 오늘처럼 두두원 로그를 받지 않으면 저희 쪽에서는 성공·실패를 구분할 수단이
   전혀 없습니다.

저희 판단이 틀렸을 수 있습니다. UPF 구성이 저희가 보는 것과 다르다면 알려 주시면 정정하겠습니다.

## 3. UDP 에 단위가 실리지 않습니다 — 해석 기준 확인 부탁드립니다

NCOF 는 `gbrDl`/`mbrDl` 을 **단위가 붙은 문자열**로 보냅니다(`"5.0 Mbps"`, `"1000.0 Mbps"`).
그런데 두두원 로그에는 이렇게 찍힙니다.

```
14_e QOS UE1 imsi=001010070000101 gbrDl=5.000000 mbrDl=10.000000
```

`std::stod()` 파싱 과정에서 접미사가 버려져 **숫자만 UDP 구조체에 실리는 것으로 보입니다.**
수신 측 UPF 가 이 `5.0` 을 **Mbps 로 읽는지 bps 로 읽는지**에 따라 10⁶배 차이가 납니다.

1. 수신 측의 해석 단위가 무엇인지 알려 주시면, **저희가 그 단위에 맞춰 보내겠습니다.**
2. 혹은 UDP 구조체에 단위 필드를 두시는 방법도 있습니다. 어느 쪽이든 맞추겠습니다.

지금은 양측 모두 이 값이 맞는지 검증할 수단이 없어, 조용히 틀릴 수 있는 지점입니다.

## 4. 후속 요청 2건 — 이번 실측으로 근거를 갱신합니다

지난 회신에서 말씀드린 `-999` 센티넬과 정수 필드 소수값입니다. **이번에 임시 보정 계층을 꺼 보고
실제로 어떻게 되는지 측정했습니다.**

**측정 방법:** NCOF 를 보정 계층 ON(20:52~21:00) → OFF(21:00~21:05) 로 기동해 같은 조건에서
비교했습니다. 거절 여부는 **두두원 로그의 `response status`** 로 교차 확인했습니다.

**(가) 두두원이 받은 응답** — 두두원 로그 `response status` 기준, **21시경 발췌 시점**입니다.

| 구간 | 응답 |
|---|---|
| 보정 계층 **ON** (20:52~21:00) | `200` ×56 · `201` ×2 · `422` **0건** |
| 보정 계층 **OFF** (직후 발췌 24건) | `200` ×10 · `422` **14건** (58%) |

(같은 로그의 응답 총계 82건 = ON 58건 + OFF 24건입니다. 발췌 시점 기준이라 이후 건수는 달라집니다.)

경로별 내역은 이렇습니다.

| 통지 경로 | 200 | 422 |
|---|---|---|
| AF (`/notifications/af/…`) | 2 | **6** |
| RICF (`/notifications/ricf/…`) | 3 | 4 |
| UPF (`/notifications/upf/…`) | 5 | 4 |

**(나) NCOF 가 보정한 양** — NCOF 수신 로그 기준. 보정 계층 ON 구간에 수신한 통지 **60건 중 40건**에
보정이 필요했고, 수리량은 이렇습니다.

```
-999 센티넬 제거      974회
정수 필드 정수화      284회  (반올림 196 · 올림 88)
단위 접미사 보정        0회  ← 9/17 수정분, 회귀 없이 유지되고 있습니다 ✅
```

**AF `PERF_DATA` 의 거절률이 가장 높은 것**은 `-999` 가 실린 필드가 약 20개로 가장 많기 때문입니다.
그중 `pdb`·`pdbDl`·`plr`·`plrDl`·`maxPdbUl`·`_jitter` 등 **14개는 전량 `-999`** 이고, 스루풋 6개
필드는 일부만 `-999` 입니다(나머지는 `"0.01 Mbps"` 처럼 정상 도착 — 아래 5절 참고).
실제로 보정 계층을 끈 5분 동안 **NCOF 가 수락한 AF 통지는 0건**이었습니다(같은 구간 RICF 5건 ·
UPF 10건 수락).

**`pdb` 계열은 반올림으로 해결되지 않습니다 — 이 점만 꼭 봐 주십시오.**
`pdb`·`pdbDl`·`maxPdbUl`·`maxPdbDl` 네 필드는 3GPP `PacketDelBudget`(정수, **최소 1**)입니다.
이번에 실제로 온 값이 `0.14`~`0.49` 구간이라 **반올림하면 `0` 이 되고, `0` 은 최소값 위반으로 다시

측정값이 없으면 해당 필드를 생략해 주십시오.

> 🔴 지난 회신과 같은 부탁입니다 — **두 항목을 함께 반영해 주십시오.** `-999` 만 먼저 고치면
> 지금 `-999` 에 가려져 있던 필드가 소수값으로 드러나 거절이 오히려 늘어납니다.

## 5. `-999` 의 성격이 드러났습니다 — 수정 방향을 다시 제안드립니다

이번 로그에서 `-999` 가 **임의로 선택한 표기가 아니라 DB 조회 실패 시의 기본값**이라는 것이
드러났습니다. 같은 구간에 이런 줄들이 함께 찍혀 있습니다.

```
[Load_Latest_Traffic_By_Id_List_Local(): 108] traffic row not found table=gnb_traffic id=gnb1
[Load_Latest_Traffic_By_Id_List_Local(): 108] traffic row not found table=gnb_traffic id=gnb2
[Apply_Dynamic_Stamp_Traffic_Values(): 513] recent dynamic stamp not found table=app_stamp ids=notebook1_ue1,…
[Apply_Dynamic_Stamp_Traffic_Values(): 544] traffic metric not found table=gnb_traffic
```

즉 **측정값이 있는 필드는 이미 정상적으로 나오고 있습니다.** 실제로 이번 회선에서는

```
dlAverageThroughput = "0.000317 Mbps"
dlPeakThroughput    = "0.212 Mbps" / "0.017 Mbps" / "0.002 Mbps" / …
traffic interval imsi=001010070000101 sec=60 deltaUl=35 deltaDl=36 avgUlBps=583.33333
```

처럼 **실측 트래픽이 단위까지 붙어 정상 형식으로** 도착했습니다(이전에는 고정 상수였습니다).
**이 부분은 아주 좋습니다.**

그래서 요청을 이렇게 좁혀 드립니다.

> **값이 없을 때 `-999` 를 넣는 대신, 그 필드를 JSON 에서 생략해 주십시오.**

이 통지가 쓰는 타입은 `PacketDelBudget`(정수, 최소 1) · `PacketLossRate`(정수, 0~1000) ·
`BitRate` 이고, 3GPP 가 "값 없음" 용으로 따로 둔 nullable `…Rm` 계열이 아닙니다. 즉 이 필드들에는
`-999` 도 `null` 도 넣을 수 없어 **필드를 생략하는 것이 규격상 유일한 방법**입니다. 문자열 타입
3종(`BitRate`/`PacketRate`/`TrafficVolume`)은 `^\d+(\.\d+)? (bps|Kbps|Mbps|…)$` 처럼 **단위 접미사가
필수인 패턴**이라 선행 `-` 자체가 들어갈 수 없습니다.

`gnb_traffic`·`app_stamp` 테이블이 채워지면 자연히 해소되는 부분이라면, 그 일정만 알려 주셔도
저희가 맞추겠습니다. 다만 `pdb`·`plr`·`_jitter` 계열 **14개 필드는 이번 구간에 실측값이 한 건도
오지 않았는데**, 이 필드들도 같은 테이블에서 채워지는 것이 맞는지만 확인 부탁드립니다.

   `20260809-08:05:12` 였습니다. 실제 실행은 9/18 이므로 gNB2 호스트의 시계가 어긋나 있는 것으로
   보입니다. 제어 이벤트를 gNB 로그와 사후 대조할 때 지장이 있어 말씀드립니다.
2. **gNB1·gNB2 의 `nrCellId` 가 동일합니다**(둘 다 `123456789`, `mcc`/`mnc` 도 동일).
   지난 회신에서 말씀드린 항목이며, 형식은 규격에 맞고 지금 제어에는 지장이 없습니다. 다만 NCGI
   기준으로는 두 gNB 가 같은 셀로 식별되어 셀 단위 집계를 넣을 때 문제가 되므로, 여유 있으실 때
   gNB 별로 다른 값을 부탁드립니다.

## 정리

| 구분 | 항목 |
|---|---|
| 🎉 확인 | **제어 2경로의 두두원 측 실행 확인**(실장비 반영은 미확인) — gNB2 `sysrepocfg` 실행 · UPF UDP 발사(UE 4) |
| ✅ 유지 | 9/17 수정 3건(소수 초 · `13p_d` 구조 · 단위 접미사) 회귀 없음 |
| 🔴 확인 요청 | ① UDP 수신 리스너 확인(관측되지 않았습니다) ② UDP 값의 해석 단위 ③ 제어 실패 시 응답 코드(`500`) |
| 🔁 후속 요청 | `-999` → **필드 생략** + 정수 필드 정수화(`pdb` 계열은 **올림**) — **동시 반영** |
| ❓ 확인 | 9/18 소스 수정 4건의 배포 계획 |
| 🤝 협조 | 재기동 시 사전 공유 — 중복 구독 보완 전까지 |
| 🔹 낮음 | gNB2 시계 · gNB 별 `nrCellId` |

`-999` 와 소수값 2건의 반영 가능 여부와 대략의 일정을 알려 주시면, 저희도 임시 보정 계층 제거
일정을 맞추겠습니다. 근거 데이터(통지 원문, 위반 집계, 이번 ON/OFF 비교 로그)는 필요하시면 바로
공유드리겠습니다.
