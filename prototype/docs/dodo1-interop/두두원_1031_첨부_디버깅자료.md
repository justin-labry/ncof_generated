### 1.5 요청
1. 손실 뒤에도 출력이 회복되도록 수정을 검토해 주십시오. 예를 들어 대기 시간이 지난 구멍은 한꺼번에 건너뛰어, 구멍마다 대기가 쌓이지 않게 하는 방법이 있을 것 같습니다.
2. `REORDER_HOLD_US`를 1초로 두신 이유가 있으면 알려 주십시오(주석의 skew p50 30 ms · p90 54 ms와 20000의 관계 포함). 20 ms는 주석의 지연 차보다 짧아 늦게 오는 경로의 패킷을 놓칠 수 있어 보여, 저희가 임의로 바꾸지는 않았습니다.
3. 괜찮으시면 저희가 노트북1에서 `REORDER_ENABLE=1`에 대기 시간만 바꿔 같은 시험(혼잡 60초 → 회복)을 해 보고 결과를 알려 드리겠습니다.
4. 15:2x에 `REORDER_ENABLE=1`로 재기동한 직후 몇 초 동안 `lo` 출력이 0이었습니다(혼잡 구간이었는지는 확인 못 함). 기동 직후 첫 순번을 잡는 방식(`startup=32`)과 관련이 있는지 봐 주시면 감사하겠습니다.

## 2. 배경 트래픽을 늘려도 노트북1에 영향이 없던 문제 — 해결 (두두원 서버 변경 알림)

### 2.1 원인 (07:34 ~ 07:38, 1초 단위 측정)
- **선로가 차지 않았습니다.** `enp131s0f1` 송신이 HIGH 구간 평균 755, 최대 812 Mbps였습니다(1442 B 프레임 기준 1G 한계 약 984). qdisc · tx 드롭은 0이었고, udptp 350M이 손실 없이 .125에 도착했습니다.
- **차더라도 흐름별로 보호되는 구조였습니다.** 기본 qdisc가 mq + 8 × fq_codel이고 XPS가 꺼져 있어, 흐름마다 해시로 HW 큐가 정해집니다(udptp 6006 → tx-0, 6007 → tx-6, .125행 GTP → tx-5, .122 → tx-3). 포화되어도 저율 GTP는 자기 몫을 받습니다(추정 — 10/22 포화 때 VoD가 무사했던 것이 근거).
- **배경 트래픽은 .125(udptp 서버)에서 끝나** 무선 구간을 타지 않습니다.
- 그래서 배경 트래픽을 더 올려 1G 포트를 채우더라도 노트북1 영상에는 영향이 없었을 것으로 봅니다(추정 — 10/31에 올린 최대치는 두 스트림 합 700 Mbps). 반대로 N3 포트 전체가 막히면 N2와 gNB2 경로도 함께 영향을 받습니다.

### 2.2 두두원 서버에서 바꾼 것

**(1) tc — Non-3GPP 용량 570 Mbps 에뮬레이션** (root, 08:15 설치, 08:34 570 적용)

.125로 가는 하향(WLAN 경로 GTP G-PDU — 그 안의 VoD와 STAMP 포함 — 와 udptp 6006/6007)만 HTB 클래스 1:10에 묶고, PIE로 같은 확률로 드롭합니다. 그래서 배경 트래픽이 용량을 넘으면 WLAN 경로 VoD도 같이 손실됩니다(WLAN 경로 STAMP도 HIGH 때 손실이 보입니다). gNB1 · gNB2 GTP, .125행 GTP echo, NGAP 등 나머지는 1:20으로 갑니다.

```bash
DEV=enp131s0f1; N3IWF=192.168.1.125
tc qdisc replace dev $DEV root handle 1: htb default 20
tc class add dev $DEV parent 1: classid 1:1 htb rate 950mbit ceil 950mbit quantum 15140
tc class add dev $DEV parent 1:1 classid 1:10 htb rate 570mbit ceil 570mbit quantum 15140
tc class add dev $DEV parent 1:1 classid 1:20 htb rate 320mbit ceil 950mbit quantum 15140
tc qdisc add dev $DEV parent 1:10 pie limit 10000 target 15ms
tc qdisc add dev $DEV parent 1:20 fq_codel
# .125 행 GTP-U G-PDU(2152, 메시지 타입 0xff — GTP echo 는 제외)
tc filter add dev $DEV parent 1: protocol ip pref 11 u32 match ip dst $N3IWF/32 match ip protocol 17 0xff match ip dport 2152 0xffff match u8 0xff 0xff at 29 flowid 1:10
# udptp 배경 트래픽
tc filter add dev $DEV parent 1: protocol ip pref 12 flower ip_proto udp dst_ip $N3IWF dst_port 6006 classid 1:10
tc filter add dev $DEV parent 1: protocol ip pref 13 flower ip_proto udp dst_ip $N3IWF dst_port 6007 classid 1:10
```

- 설치 전 상태는 두두원 서버 `~/tc_before_2026-10-31_0815.txt`에 남겨 두었습니다(같은 곳의 빈 파일 `tc_before_2026-10-31_0833.txt`는 작업 중 실수로 생긴 것이라 지우셔도 됩니다).
- PIE를 쓴 이유: tc police(토큰버킷)로는 udptp의 64패킷 묶음이 토큰을 먼저 써서 드롭이 udptp에 몰리고, 묶음 사이에 온 VoD는 대부분 통과해 VoD 손실이 조건에 따라 4 ~ 23%로 들쭉날쭉했습니다(시뮬레이션). PIE는 들어오는 모든 흐름을 같은 확률로 버립니다.
