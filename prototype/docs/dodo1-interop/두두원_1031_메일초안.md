**1. 노트북1 poc_router — 패킷 손실 뒤 영상이 계속 멈추는 문제 (확인 요청)**
- 시연용으로 WLAN 경로에 혼잡을 걸어(아래 2번) 노트북1 WLAN 경로에서 패킷이 빠지게 했습니다.
- 손실이 없을 때는 정상입니다. 그런데 패킷이 빠지면 영상이 멈추고, 혼잡이 끝나도 다음 혼잡(약 2분 30초 뒤)까지 회복되지 않아 계속 멈춰 있었습니다.
- `poc_router` 재정렬이 빠진 GRE 순번을 기다리느라 따라잡지 못하는 것으로 보입니다. 멈춘 상태에서 `lo` 출력이 1초 간격으로 2~3개씩만 나왔고(혼잡 중 측정), 설정은 `REORDER_HOLD_US=1000000`입니다(주석에는 20000).
- 임시로 `REORDER_ENABLE=0`(재정렬 끔)으로 운용 중입니다. 이 상태에서는 혼잡 때 멈췄다가 혼잡이 풀리면 회복합니다.
- 손실 뒤에도 회복되도록 수정을 검토 부탁드립니다(요청 사항은 첨부 1.5).
- 재기동하면서 보니 노트북1 `config/xrouter.conf`의 DEV 주소가 노트북2 주소(102.10/104.10)로 되어 있어 101.10/103.10으로 고쳤습니다. 돌던 프로세스는 노트북1 주소로 정상 동작 중이었습니다. 기존 `poc_router`(pid 527232)는 끄고 터미널 창에서 다시 띄웠습니다(창을 닫으면 멈춤). 바꾼 것과 되돌리는 방법은 첨부 1.6에 있습니다.

**2. 배경 트래픽을 늘려도 노트북1에 영향이 없던 문제 — 해결 (두두원 서버 변경 알림)**
- 배경 트래픽(udptp)을 700 Mbps까지 올려도 노트북1 영상은 그대로였습니다. 배경 트래픽이 .125(Non-3GPP 액세스)에서 끝나 무선 구간을 타지 않고, 두두원 서버 N3 포트(1G)도 차지 않았기 때문입니다. 차더라도 흐름별 큐라 영향이 작은 구조여서, 더 올려도 효과가 없었을 것으로 봅니다(첨부 2.1).
- 그래서 두두원 서버 `enp131s0f1`에 tc를 걸어 .125 방향(WLAN 경로 GTP + udptp)만 570 Mbps로 제한했습니다. Non-3GPP 용량을 흉내 낸 것입니다. 또 `~/NW_Collect/iperf_Test2/run_client.sh`를 계단형(스트림당 50M 60초 → 150M 90초 → 350M 60초)으로 바꿨습니다. 원본은 `run_client.sh.bak-20261031`입니다.
- 결과: 배경 트래픽이 많을 때 노트북1의 WLAN 경로만 손실이 나고, 노트북2는 NCOF가 미리 gNB2로 옮겨 원활합니다.
- tc는 재부팅하면 사라집니다. 서버를 재부팅하시면 알려 주십시오. 저희가 다시 걸겠습니다(명령은 첨부 2.2).
